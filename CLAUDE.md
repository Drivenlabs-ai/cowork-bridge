# cowork-bridge

Outil Drivenlabs : pont **Google Drive → dossier local plat → Claude Cowork** sur Windows. Déployable chez les clients.

## Problème résolu

Le sandbox de Claude Cowork (VM Hyper-V, montage hôte→VM en **virtiofs / Plan 9**) attend du NTFS standard. Google Drive (et OneDrive/Dropbox/iCloud) expose ses fichiers via un filesystem virtuel / Cloud Files API → le montage échoue (`EINVAL`) ou la VM ne traverse pas la projection → **dossier vu vide dans Cowork**. Limite connue, non corrigée par Anthropic (issues `area:cowork` du repo `anthropics/claude-code`, ex. #25293, #29583, #33590). Contraintes Cowork aggravantes : dossier de travail **obligatoirement dans le home** (`C:\Users\<user>\`), et **raccourcis/jonctions rejetés** (résolus via `realpath()` puis re-bloqués).

Conséquence : seule issue stable = donner à Cowork un vrai dossier local plat dans le home, alimenté automatiquement depuis Drive.

## Architecture (Archi A : rclone sur le dossier Drive Desktop)

```
cloud <->[Google Drive Desktop, mode STREAM]<-> Mon Drive\X <->[rclone bisync, local<->local]<-> %USERPROFILE%\CoworkWork\X -> Cowork
```

- **Moteur = rclone** (licence MIT, **bundlé** dans l'installeur). `rclone bisync` entre DEUX chemins locaux (dossier monté par Drive Desktop ⇄ dossier de travail) — **aucun OAuth, aucun remote**. Choix vs FreeFileSync : FFS interdisait le bundling et l'usage pro de l'édition gratuite ; rclone est librement redistribuable.
- **Mode Stream, pas Miroir** : tout le Drive reste en placeholders ; seuls les dossiers pontés sont hydratés. Stockage local ≈ Σ(dossiers suivis).
- **Ciblage** : ajout **par l'explorateur** (`Select-DriveFolder`, OpenFileDialog détourné). Avant chaque ajout : **garde-fou disque** (`Test-DiskBudget` / `New-BrowsedSource`) — refuse si le dossier ne tient pas sur C: avec une marge (`$DiskMarginBytes` ≈ 5 Go). **Critique** : un disque plein empêche Windows de charger le profil → session vierge (incident Dylan).
- **Synchro de fond** : **agent résident unique** (`Set-SyncAgent` → `_bridge\sync-agent.ps1`, sans droits) = `FileSystemWatcher` (push quasi instantané, récupéré par **`Wait-Event`** qui pompe la file — pas `-Action`+`Start-Sleep` qui ne déclenche pas en `-File`) **+** timer toutes les N min (pull). Relit `config.json` + `_bridge\interval` à chaque tour (délai à chaud, ajout/désync pris en compte sans redémarrer l'agent), écrit `_bridge\next-sync` (minuteur). Mono-instance par **mutex nommé** (`Local\CoworkBridge-SyncAgent`). **Chien de garde** : tâche planifiée per-user `CoworkBridge-Watchdog` (logon + toutes les heures, sans admin, `ExecutionTimeLimit` illimité) relance l'agent s'il est mort — le doublon sort immédiatement via le mutex ; repli raccourci Démarrage si la création de tâche est bloquée (GPO). L'agent est **stoppé avant** tout swap de filtres / désync (tâche désenregistrée d'abord, pas de relance pendant la fenêtre) et **toujours réinstallé en `finally`** (`Apply-Config`, refresh de `Start-Bridge`, `Remove-TrackedFolder`) : une exception au milieu ne peut plus laisser la machine sans agent ni watchdog. Tâche via identité `WindowsIdentity` (correcte sur AzureAD) + `RepetitionDuration` finie (10 ans).
- **Sûreté des données** (flags rclone sourcés) : tout resync = `bisync --resync --resync-mode newer` (**union**, jamais d'effacement Drive, la version la plus récente gagne — au 1er run le local vient d'être créé vide → Drive fait foi de fait). Garde-fous : `--check-access` + marqueur `.coworkbridge-ok` des deux côtés (abort si un côté vu vide/non monté), `--max-delete 100` (**aucun seuil de suppression** : le dossier local reflète le Drive, suppressions comprises — décision Alex 2026-07-26 ; le garde à 25 % gelait un geste métier ordinaire, retirer un dossier client pesant plus que 25 % d'une paire), `--conflict-resolve none` (garde les 2 versions), `--backup-dir2` local daté (équivalent corbeille) + corbeille Drive native côté Drive, `--resilient --recover --max-lock 2m --retries-sleep 30s`. Projection Drive : `--local-no-preallocate` (bug « sizes differ » +N octets, rclone #3207) + `--local-no-check-updated` (placeholder qui s'hydrate pendant la lecture), `--checkers 1` (ERROR 1450, pool noyau cldflt). Journal borné : `--log-file-max-size 5M --log-file-max-backups 2` (rotation native rclone v1.71+). Désync (`Remove-TrackedFolder`) = `rclone copy` local→Drive (copie seule, gardé sur exit 0) puis corbeille du local + purge de l'état de la paire.
- **Récupération & filtres** : bisync hash le filters-file (`filters.txt.md5`) et abort « filters file has changed (must run --resync) » si le contenu change → `New-FiltersFile` détecte le changement et `Reset-PairBaselines` invalide les `*.synced` → resync `newer` au passage suivant (indispensable à chaque update qui touche les filtres). Abort critique (exit code 7) = jeton one-shot `<paire>.resync-pending`, armé au 2ᵉ exit 7 consécutif, max 1 auto-resync/fenêtre (`$RecoveryGateHours`)/paire (pas de tempête). **Baseline de paire** : `<paire>.synced` est écrit dès qu'un run sort en **0 ou 1**. Exit 1 = échec non critique, bisync a sauvegardé ses listings (seul `b.critical` renomme en `.lst-err`, source v1.74.3) : la paire A sa baseline. Le conditionner au seul exit 0 enfermait une paire à erreur fichier récurrente en `--resync` perpétuel — donc en **union permanente**, où les ajouts passent et **aucune suppression ne passe jamais**, sans autre signal que le compteur d'échecs. **Suppressions massives** : le garde `--max-delete` étant désactivé (100), l'abort « too many deletes » ne peut plus se produire ; la détection par offset de log (`Get-LogOffset` + `Test-MaxDeleteSignal -FromOffset`) et le jeton `<paire>.force-pending` restent en place, inertes, comme filet si le seuil était un jour rétabli. **Seuils de tuning** (`$RecoveryGateHours` 24 h, `$RecoveryConsecutive` 2, `$FailThrottle` 3) = source unique sérialisée dans l'agent (comme les flags) → pas de dérive installeur/agent. **« Sync now » manuel** = override humain : `Sync-Pair -Manual` escalade inline (run → si exit 7 resync, si too-many-deletes force) en bypassant les gates → débloque une paire coincée sans attendre la fenêtre.
- **Observabilité** : statut par paire `_bridge\status\<nom>.json` (lastRun, lastExit, lastSuccess, failures consécutifs, lastAutoResync, deleteAborts, lastAutoForce) écrit par l'agent et par le panneau, **read-modify-write sérialisé par mutex** `Local\CoworkBridge-Status` (l'écriture atomique seule ne protège pas d'une mise à jour perdue). Le panneau affiche l'état réel, à états **ordonnés** : agent arrêté > FAILING (erreur réelle, ≥ `$RecoveryConsecutive` échecs) > « waiting for Google Drive to start » (sentinelle Drive absent) > « syncing (retrying) » (1er échec) > vert « last sync OK ». Recalcul ~1×/5 s (le compte à rebours reste à 1 s). Lisible à distance pour le support.
- **Code Drive absent** : quand le chemin Drive n'est pas monté, `Sync-Pair`/l'agent retournent la **sentinelle `$CodeDriveMissing = 90`** (hors plage rclone 0-10) — pas de run, pas d'exit 7 transitoire. NEUTRE : n'incrémente pas `failures` (pas de faux rouge au boot, pas de blocage FSW). Agrégée par **sévérité** (`Merge-SyncCodes`, pas `max` numérique) → ne masque jamais un abort réel 1/7.

⚠️ **Risque assumé d'Archi A** : on garde la couche Drive Desktop stream → le risque placeholder (hydratation, « placeholder vu comme supprimé ») persiste. `--check-access` couvre « dossier entier vide », pas le placeholder individuel → **test Windows bloquant**. Archi B (rclone direct API, sans Drive Desktop) éliminerait ce risque mais a été écartée (friction OAuth + coût vérification Google « restricted scope » : CASA $500–4 500/an, ou client_id par client).

## Fichiers

- `Run-CoworkBridge.bat` — lanceur (PowerShell `-STA -ExecutionPolicy Bypass`).
- `Install-CoworkBridge.ps1` — installeur + **centre de contrôle** WinForms (PS 5.1, pas de PS7). Moteur **rclone** (`Find-Rclone` → `rclone.exe` bundlé à côté du script). Install : choix des dossiers par l'explorateur + garde disque → `Apply-Config` (filtres, marqueurs, 1ʳᵉ synchro `bisync --resync`, agent). Si install existante → **panneau de gestion** : liste suivis, **Ajouter**, **Désynchroniser** (`Remove-TrackedFolder` : `rclone copy` local→Drive puis corbeille), **délai à chaud**, **minuteur**, Synchroniser, Ouvrir, MAJ, Désinstaller. `Apply-Config` factorisé. **Migration FFS→rclone au lancement** (`Test-NeedsMigration`/`Invoke-LegacyMigration`) : une config v1 (FreeFileSync) déclenche, avant le panneau, l'arrêt de RealTimeSync, la purge des fichiers d'état `.ffs_*` côté local (jamais le Drive ; les `.ffs_db` volatils cassaient rclone — « corrupted on transfer », cas Dylan), la déduplication des sources par chemin, puis un `Apply-Config` rclone (baseline `--resync`, filtres FFS exclus, agent) — indispensable car les clients en prod sont sur FFS et s'auto-updateront vers rclone. Les filtres rclone (deux groupes source-unique : `$VolatileFilterLines` = éphémère qui casse la sync, `$DirFilterLines` = artefacts dev `.git`/`node_modules`/… ; `filters.txt` = les deux concaténés) excluent aussi `*.ffs_*`. **La désync applique un filtre VOLATILE seulement** (`New-DesyncFilterFile` → `desync-filter.txt`, via `--filter-from`) : les dossiers dev n'existent que localement, on les **rend au Drive** avant de recycler le local (sinon ils finiraient à la corbeille — le dialogue promet « renvoyé sur Drive »). La désync n'utilise **pas** `--local-no-check-updated` (on VEUT l'abort si un fichier est en cours d'écriture, sinon on pousserait un tronqué avant de supprimer le bon). Génère l'agent via `Set-SyncAgent` (here-string `@"..."@` → `$` des variables de l'agent **backtické** ; seuls `$rcLit`/`$metaLit`/`$markLit`/`$safetyLit`/`$perfLit`/`$logLit` interpolés ; chemins échappés `''`). Pièges PowerShell : `ConvertFrom-Json` peut rendre les dates ISO en `[datetime]` selon l'hôte (PS7 ; PS 5.1 les laisse en chaîne) → re-normaliser en chaîne `'o'` avant `ConvertTo-Json` et caster `[datetime]$x` (jamais `::Parse`, dépendant de la culture) ; `Test-Path`/`Get-Content`/`Remove-Item` globbent (`[ ]` légaux dans un nom Windows) → **`-LiteralPath` obligatoire** sur tout chemin dérivé d'un nom de dossier client. **⚠ UTF-8 AVEC BOM obligatoire** (PS 5.1 lit sans BOM en ANSI → accents cassés ; réajouter `printf '\xEF\xBB\xBF'`). Sécurité : `Assert-SafePath` (rejette CR/LF, `"`) sur tout chemin avant génération ; sinks `Start-Process` utilisent l'exe re-résolu, jamais un chemin de config ; `Test-UnderHome` rejoué avant toute création/suppression.
- `GUIDE.md` — guide client + checklist de déploiement Drivenlabs.
- `setup.iss` — script Inno Setup → installeur Windows pro (per-user, sans admin ; menu Démarrer, désinstalleur, lance la config au « Terminé »). Compilé sur Windows (CI ou machine Windows), pas sur Mac.
- `.github/workflows/build.yml` — CI : runner Windows compile l'installeur, signe si secrets présents, publie l'artefact (et une Release sur tag `v*`).
- `.gitignore` — ignore `Output/`, `*.exe`, `*.pfx`.

État runtime chez le client : `%USERPROFILE%\CoworkWork\_bridge\` (`config.json`, `sync-agent.ps1`, `filters.txt` [+ `filters.txt.md5` écrit par bisync], `interval`, `next-sync`, `bisync-state\` [listings rclone + `<paire>.synced` baseline + `<paire>.resync-pending` / `<paire>.force-pending` jetons de récupération], `status\<paire>.json` [état de synchro : lastRun/lastExit/lastSuccess/failures/lastAutoResync/deleteAborts/lastAutoForce], `trash\<date>\` [backups], `rclone.log` [roté 5M×2], `bridge.log`). Tâche planifiée per-user `CoworkBridge-Watchdog`. Marqueur `.coworkbridge-ok` dans chaque dossier suivi (local + Drive) pour `--check-access`.

## Build & distribution (pro)

- **Compilation** : sur Windows uniquement (`ISCC.exe setup.iss`), via la CI (runner `windows-latest`). Sortie : `Output\CoworkBridge-Setup.exe` (nom **stable**, sans version → URL latest permanente).
- **CI = build + release** (`.github/workflows/build.yml`) : à CHAQUE push sur `main`, version **par date** `YYYY.M.D.N` (N = nombre de commits du jour, auto), build de l'exe, `CHECKSUM` SHA256, puis **Release GitHub** (tag `vYYYY.M.D.N`) avec assets `CoworkBridge-Setup.exe` + `CHECKSUM` + `VERSION`. Plus de tag manuel, plus d'Azure. Versionné via `ISCC /DMyAppVersion /DMyAppVersionInfo`.
- **Mise à jour (pattern dentalsoft, appliqué à l'exe)** : l'app, au lancement (`Invoke-UpdateCheck` au début de `Start-Bridge`) **et** via le bouton « Vérifier les mises à jour », interroge `releases/latest` (repo public → API anonyme), compare la `VERSION` installée (lue dans `{app}\VERSION`, shippée par `setup.iss`) à la dernière release ; si plus récente → télécharge l'exe, **vérifie le SHA256** contre `CHECKSUM`, `Unblock-File`, le lance → Inno met à jour **en place** (AppId stable, config + données dans le profil conservées). Intégrité par **checksum**, pas par signature.
- **Signature de code : reportée** (jugée trop lourde pour l'instant). Conséquence assumée : l'exe non signé déclenche l'avertissement SmartScreen « éditeur inconnu » au 1er lancement. Voie moderne si on la veut un jour : **Azure Artifact Signing** (HSM cloud, ~9,99 $/mois, éligible UE, action `azure/trusted-signing-action@v2`, 6 secrets `AZURE_*`) — depuis juin 2023 plus de `.pfx`, signature cloud obligatoire. À rebrancher comme étape CI séparée le moment venu.
- **Moteur rclone bundlé** : la CI (étape `Bundle rclone`) télécharge `rclone-v<ver>-windows-amd64.zip` (version épinglée v1.74.3), **vérifie le SHA256 contre le `SHA256SUMS` officiel de rclone** (pas de hash en dur), extrait `rclone.exe` + la notice MIT (`rclone-LICENSE.txt`) ; `setup.iss` les embarque. Licence MIT → redistribution commerciale + bundling autorisés (seule obligation : joindre la notice). Bumper la version = changer `$ver` dans `build.yml`.
- **Icône** : `assets\app.ico` (lignes commentées dans `setup.iss`) — déposer le `.ico` Drivenlabs pour le branding, puis décommenter.

## Déploiement client (checklist interne)

Note : le repo est public, donc le `GUIDE.md` est grand public — cette checklist vit ici, pas dans le guide.

1. **Prérequis machine** : Google Drive pour ordinateur (mode **« Accéder en ligne aux fichiers »**, surtout pas « Dupliquer les fichiers »). **Seul prérequis** — le moteur rclone est bundlé dans l'installeur.
2. Donner au client l'`.exe` (Release GitHub). Non signé → avertissement SmartScreen « éditeur inconnu » au 1er lancement (et désormais aussi sur les auto-updates, `Unblock-File` retiré) — prévenir le client.
3. Installer → cocher les dossiers métier + Drive partagés pertinents → connecter `CoworkWork` dans Cowork.
4. **Valider** : ouvrir Cowork, vérifier que les fichiers sont **lisibles** (pas seulement listés — ouvrir un doc).
5. Noter l'empreinte stockage = somme des dossiers cochés.

Libellés Google Drive FR vérifiés (source officielle Google, juin 2026) : stream = « Accéder en ligne aux fichiers », miroir = « Dupliquer les fichiers », chemin « Paramètres → Préférences → Dossiers de Drive → Options de synchronisation de Mon Drive ». À reconfirmer sur la build installée chez le client (les libellés ont changé selon les versions).

Limites connues :
- Vaut pour Windows. Sur Mac le même mur existe (FileProvider) — rclone est cross-platform, mais l'installeur/PS (WinForms + agent FSW) est Windows-only (à porter si besoin).
- C'est un **contournement**, pas un correctif Anthropic. À retirer le jour où Cowork supportera nativement les dossiers cloud (issues `area:cowork` du repo `anthropics/claude-code`).
- Collision de noms de dossiers locaux : `Build-Pairs` trie de façon déterministe (stable dans tous les cas réalistes) ; un rename théorique ne survient que si deux dossiers de même type sanitizent vers le même nom (caractères illégaux) — quasi nul, non corrigé (réutiliser `LocalName` persisté fermerait le trou si besoin).
- **Une suppression peut être annulée par un pair qui a modifié le fichier.** Règle de bisync, délibérée et **non paramétrable** (`--conflict-resolve` ne couvre que modif contre modif) : `Path1 deleted AND Path2 changed → Path2 version survives → rclone copy Path2 to Path1`. Chaque poste tenant une copie complète en lecture-écriture du même dossier Drive, **il suffit qu'un seul poste ait touché le fichier depuis sa dernière baseline pour que la suppression remonte** — le fichier repart sur le Drive puis redescend chez les autres. Fenêtre = de la dernière synchro réussie de ce poste à l'arrivée de la suppression ; un poste éteint ou en veille l'élargit à des jours. Sortir de là suppose de quitter la table de bisync (réimplémenter la réconciliation) ou de changer la topologie (un seul poste en écriture, les autres en miroir descendant) — **arbitrage produit ouvert, à trancher avec le client**.
- **Une paire qui ne réussit jamais son `--resync` reste en union.** Un resync qui échoue sur un seul fichier illisible abort de façon critique (exit 7) : `--resilient` **ne s'applique pas** pendant un resync (`if b.retryable && b.opt.Resilient && !b.opt.Resync`), et `--ignore-errors` ne sauverait rien (il ne conditionne que les suppressions, l'erreur remonte quand même — source vérifiée). La paire ne peut alors pas acquérir de baseline et rejoue un resync-union à chaque passage. Le panneau passe au rouge (FAILING) mais la synchro « a l'air » de marcher : ajouts et modifications continuent. **Pas de correctif à coût raisonnable** : identifier le fichier fautif dans `rclone.log` et l'exclure.
- L'auto-update ne se déclenche qu'à l'ouverture de l'app (statu quo décidé 2026-07-02 : l'update silencieux par l'agent exigerait la signature de code — Azure Trusted Signing — sinon SmartScreen casse le silencieux ou il faut retirer le marquage de sécurité, refusé en revue sécurité).
- Une modification utilisateur faite PENDANT une synchro perd le push instantané (file FSW purgée post-run pour ne pas doubler les scans de la projection) — elle part au tick d'intervalle suivant, ou à la modification suivante.
- **Tout `--resync` ressuscite les suppressions non encore propagées** — c'est une **union** (`--resync-mode newer` : la version la plus récente gagne, rien n'est jamais supprimé), et aucun mode de resync n'y échappe (la séquence est `copy Path2→Path1 --ignore-existing` puis `copy Path1→Path2`). Déclencheurs restants : changement de `filters.txt` (l'update qui touche les listes de filtres invalide les baselines de **toutes** les paires) et jeton `.resync-pending` après 2 exits 7 consécutifs. **Conséquence opérationnelle : ne jamais modifier `$VolatileFilterLines` / `$DirFilterLines` sans le vouloir** — un update qui les touche déclenche une union chez tous les clients, donc une résurrection de masse. **Accepté** : inhérent au resync de bisync.

## Détails techniques vérifiés (rclone, audits 2026-06-21 et 2026-07-02, sources rclone.org + source v1.74.3)

- **bisync par paire** (1 appel par dossier suivi), local↔local : `rclone bisync "<Drive>" "<Local>" --workdir <_bridge\bisync-state> --filters-file <_bridge\filters.txt> --check-access --check-filename .coworkbridge-ok --max-delete 100 --conflict-resolve none --backup-dir2 <_bridge\trash\<date>\<name>> --checkers 1 --transfers 4 --local-no-preallocate --local-no-check-updated --retries-sleep 30s --resilient --recover --max-lock 2m --log-file <_bridge\rclone.log> --log-level INFO --log-file-max-size 5M --log-file-max-backups 2`. Resync (1er run, récupération, filtres modifiés) : `+ --resync --resync-mode newer`.
- **Sûreté (vérifié doc)** : `--resync` est requis au 1er run et est une **union** (jamais de suppression côté Drive) ; `--conflict-resolve none` (défaut) garde les deux versions renommées `…conflict1/2` ; `--max-delete` en bisync = **pourcentage**, pas un nombre (défaut 50 %, on met **100** = jamais d'abort ; source `deltas.go/excessDeletes` : `curRatio = deleted / oldCount`, abort si `curRatio > maxRatio`). Son abort met `b.abort` et **pas** `b.critical` (`operations.go` l.348-352) → **exit 1**, listings **préservés** (pas de `.lst-err`) — la doc rclone laisse croire à un abort critique, c'est faux ; le message émis est `Safety abort: too many deletes (>N%, x of y) ...` ; `--check-access` exige le marqueur des deux côtés AVANT le 1er resync (sinon il échoue) → on pose `.coworkbridge-ok` des deux côtés, et il **n'est PAS** exclu des filtres : `--check-access` applique `filters.txt`, donc l'exclure le rendait introuvable → abort systématique (vérifié sur Windows). Le marqueur se synchronise donc (inerte) ; ne PAS utiliser `--inplace` ; ne JAMAIS setter `--multi-thread-streams` (réactiverait le multi-thread, désactivé par défaut en local↔local) ; pas de `--max-duration`/`--cutoff-mode` (fabrique un abort critique non-retryable en bisync) ; pas de `--checksum` (lirait tout → hydratation massive de la projection). Exit codes bisync : 0=ok, 1=non critique, 2=usage, **7=abort critique (« Must run --resync to recover »)**. bisync = « advanced command », jamais déclaré production-ready → ≥ v1.66 (on épingle v1.74.3).
- **Filters-file hashé** : bisync stocke `filters.txt.md5` à côté du fichier et abort « filters file has changed (must run --resync) » à chaque run si le contenu change (garde-fou : un fichier nouvellement exclu serait sinon vu « supprimé » et supprimé pour de vrai). Aucun flag de contournement. Sortie propre = resync — d'où `New-FiltersFile` (détection de changement) + `Reset-PairBaselines`.
- **Bugs projection Drive Desktop (diag logs clients 2026-07-01)** : (1) préallocation Windows arrondie au secteur → la projection rapporte la taille préallouée → « corrupted on transfer: sizes differ » (+20 octets = arrondi 512) → `--local-no-preallocate` (rclone #3207) ; (2) `ERROR 1450 Insufficient system resources` sur `GetFileInformationByHandleEx` à l'énumération (pool noyau cldflt, frappe des dossiers précis, non documenté côté rclone) → mitigation `--checkers 1`, non prouvée ; (3) lecture d'un placeholder en cours d'hydratation → « can't copy - source file is being updated » → `--local-no-check-updated`.
- **Agent** : `Wait-Event -Timeout 5` (pompe la file FSW + tick périodique). `Register-ObjectEvent` SANS `-Action` (les events se mettent en file ; `-Action`+`Start-Sleep` ne déclenche pas en `-File`).
- Détection Drive : scan des racines de lecteurs + home, recherche d'un enfant `My Drive`/`Mon Drive` et `Shared drives`/`Drive partages`.

## État

Revue 1 (3 relecteurs : correction, sécurité, UX) et correctifs : 1er run en Miroir (anti-effacement Drive), suppressions corbeille + gate sur exit code, confinement réel du chemin (`GetFullPath`), `sources=@(...)` (cas mono-dossier), `LogfileFolder` revenu à la forme format-13 vérifiée, tâche planifiée `-User`, filtrage des lecteurs prêts, BOM UTF-8 + accents, wording client dé-jargonné, mise en avant « connecter CoworkWork, pas le dossier Drive ».

Revue 2 (post-packaging, CI + régression PS) et correctifs : **B1** la désélection supprimait par nom recalculé sans suffixe anti-collision → on persiste `LocalName` en config et on supprime par nom stocké ; **M1** la synchro finale de désélection était TwoWay (pouvait propager une suppression vers Drive) → remplacée par un batch **Update local→Drive** (copie seule, jamais de suppression) ciblé sur les dossiers retirés, gardé sur exit code ; CI durcie : moindre privilège (`contents: read` global, `write` au seul job release), garde anti-release-non-signée sur tag, actions épinglées par SHA, Inno pinné 6.7.1, PFX en `try/finally`, `VersionInfoVersion` numérique dédié. `setup.iss` : tous les points Inno vérifiés corrects. Note connue : l'`[UninstallRun]` fait `Stop-Process RealTimeSync` global (tue toutes les instances RTS, pas seulement la nôtre — pas de PID tracking ; acceptable car les clients ne lancent pas d'autre RTS).

**Suppressions qui remontent — blocage client (2026-07-26)** : un fichier supprimé revient. La lecture du client (« le pont d'un collègue le republie ») est exacte mais n'est qu'un des chemins. Diagnostic complet : `tasks/diagnostic-2026-07-26-suppressions.md`. Trois mécanismes distincts, tous établis sur le code livré + la source rclone v1.74.3 : (1) **règle de bisync** — une modification bat une suppression (`Path1 deleted AND Path2 changed → Path2 survives`), non paramétrable, et il suffit d'UN poste ayant touché le fichier ; (2) **union permanente** — `<paire>.synced` n'était écrit que sur exit 0, donc une erreur fichier récurrente enfermait la paire en `--resync` à chaque run : ajouts propagés, aucune suppression jamais ; (3) **`--max-delete 25`** — un pourcentage, franchi par un simple retrait de dossier client, qui abandonnait le run entier. Livré : (2) baseline acquise sur exit 0 **ou 1**, (3) seuil supprimé (`--max-delete 100`, décision Alex). (1) **reste ouvert** — arbitrage produit (topologie) à poser au client, voir Limites. **Cette décision annule celle du 2026-07-02** (auto-force des suppressions massives, confirmation en 2 signaux consécutifs) : sans seuil, l'abort ne se produit plus, donc la confirmation en deux temps ne s'arme plus jamais. Le mécanisme (`Test-MaxDeleteSignal`, jeton `.force-pending`, drapeau `--force`, champs `deleteAborts`/`lastAutoForce`) est **laissé en place et signalé inerte dans le code**, pour ne pas ouvrir un gros diff la veille d'une session ; le retirer suppose de purger aussi les jetons et les champs de statut, à faire après le banc Windows. Filtres volontairement **non touchés** : les modifier aurait déclenché un resync-union chez tous les clients, donc une résurrection de masse au moment même du correctif.
